# 確認事項の一覧

> 用語は [`00-glossary.md`](00-glossary.md) で定義しています。

## このページの使い方

**社内環境に戻ったら、このページを持ってサーバ側の担当者に確認してください。**

サーバ側の実物の仕様が未入手のため、
このリポジトリの仕様は**ほぼすべてこちら側の想定**で書かれています。
その「想定した箇所」を、確認しやすい順に並べたのがこのページです。

各項目には次を書いています。

- **知りたいこと** — 何を聞けばよいか
- **なぜ必要か** — 答えによって何が変わるか（相手に説明するときに使えます）
- **分からない間の仮置き** — いまの仕様がどう書かれているか
- **影響範囲** — 答えが違ったとき、どこを直すことになるか

### 確認が済んだら

1. 該当する仕様の記述を直す
2. 確定度マーカーを 🔴 から 🟢 に上げる<!--legend-->
3. **この項目に「✅ 確定」と結論を追記する**（消さないでください。判断の経緯が残ります）
4. [`CHANGELOG.md`](CHANGELOG.md) に記録する

### 進捗の確認

```sh
bash scripts/check-spec.sh
```

確定度マーカーの集計が出ます。**件数をこのページに手で書かないでください。**
必ず古くなり、どちらが正しいのか分からなくなります。

## Q-001 計画ファイルの実物が欲しい

**知りたいこと**: 実際の計画ファイルを 1 つ（できれば 2〜3 種類）もらいたい。
機密であればダミーデータに置き換えたもので構いません。

**なぜ必要か**: このツールは計画ファイルを読んで表示するものなので、
**ファイルの構造が分からないと画面が一切作れません。**
要素名・属性名・値の形式すべてがこれに依存します。

**分からない間の仮置き**: [`interface/20-data-model.md`](interface/20-data-model.md) に
想定の構造を書き、[`interface/examples/portfolio-example.json`](interface/examples/portfolio-example.json)
にサンプルを置いています。**すべて架空のものです。**

**影響範囲**: データモデルの章の全体、ガントチャート・ネットワーク図の全操作。
**このリポジトリで最も影響が大きい項目です。**


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **一部確定。** 計画ファイル（XML）そのものは画面側に来ないことが分かった。
> サーバ側が解析して JSON（`GET /portfolio`）で返す。実物の JSON の例は受領済み。
> XML の実物はもはや画面側には不要。ただし**実データでの動作確認はまだ**（受領したのは文書のみ）。

## Q-004 計画ファイルをどう指定して開くのか

**知りたいこと**: サーバ側は、どうやって開くファイルを知るのか。

1. ファイルのパスを受け取って、サーバ側が読む
2. ファイルの中身を受け取る
3. サーバ側が「開けるファイルの一覧」を持っていて、そこから選ばせる

また、開いた計画に識別子（`planId`）を発行して状態を保持するのか、
それとも毎回ファイルを読み直すのか。

**なぜ必要か**: **ブラウザは安全上の理由から、利用者が選んだファイルの
絶対パスを画面側に教えてくれません。**
そのため「パスを指定する」方式にするなら、利用者に手で入力してもらうか、
サーバ側が候補一覧を返す必要があります。**ファイルを開く画面の作りが根本から変わります。**

**分からない間の仮置き**: パス指定方式で書いています
（[`interface/openapi.yaml`](interface/openapi.yaml) の `POST /plans`）。

**影響範囲**: [`ui/10-screens.md`](ui/10-screens.md) のファイルを開く画面、
`POST /plans`、`DELETE /plans/{planId}`。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **確定。開く操作は無い。** サーバ側が自分の置き場所（`sourcePath`）の XML を読む。
> どのプロジェクトを見るかは、ホスト画面から起動クエリ `projectIds` で渡されてくる。
> `planId` は常に `bm3-portfolio`。ファイルを開く画面（`UI-OPEN-*`）は廃止。

## Q-003 XML をどういう形で受け渡すのか

**知りたいこと**: 計画の XML は、次のどちらの形でやり取りするのか。

- **案 A**: JSON の中の文字列として入れる（`{"xml": "...", "revision": "r7"}`）
- **案 B**: HTTP の本文をそのまま XML にする（`Content-Type: application/xml`）

**なぜ必要か**: `revision`（版の印）を XML と一緒に運ぶ必要があるためです。
案 A なら本文に同梱できます。案 B なら `ETag` ヘッダーで運ぶことになります。

**分からない間の仮置き**: **案 A を採用**しています。付帯情報を一緒に運べて、
取り違えが起きにくいためです。`openapi.yaml` には**両方書いてあり**、
確定したら片方を消せば済むようにしてあります。

**影響範囲**: すべての API の要求と応答の形。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **確定。案 A でも案 B でもなく、サーバ側が XML を JSON に変換して返す。**
> 画面側は XML の要素名を一切知らなくてよい。`revision` は JSON の一項目として来る。
> 保存側の形は未実装のため未定（`Q-015`）。

## Q-005 保存時に版を照合できるか（他人の変更を消す事故の防止）

**知りたいこと**: サーバ側は次に対応できるか。

- 計画を返すときに「版」を示す値（`revision` / `ETag`）を返す
- 保存時に `If-Match` を受け取り、食い違えば `409` を返して**保存を拒否する**

**なぜ必要か**: このツールは **XML を全文置き換え**する設計です。
そのため対策がないと、**後から保存した人が、前の人の変更を黙って消します。**

同じファイルを 2 つのウィンドウで開いた場合など、
一人で使っていても起こり得ます。計画ファイルは重要なので、この事故は避けたいところです。

**対応できない場合の落としどころ**:
- サーバ側でファイルの更新時刻を見て、読み込み後に変わっていれば警告する
- それも無理なら、画面側で「読み込んでから時間が経っています」と注意を出す程度

**分からない間の仮置き**: 対応している前提で書いています
（`PUT /plans/{planId}` で `If-Match` を必須にしている）。

**影響範囲**: `PUT /plans/{planId}`、[`ui/13-diff.md`](ui/13-diff.md) の `UI-DIFF-06`、
[`interface/23-sequences.md`](interface/23-sequences.md) の流れ 2。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **一部確定。** `GET /portfolio` の応答に `revision` があり、
> サーバ側の文書に「将来保存 I/F で使用予定」とある。版の照合は**実現できる見込み**。
> `If-Match` で受け取るかどうかは、保存 I/F が実装されるまで不明。

## Q-011 クリティカルチェーンは誰が計算するのか

**知りたいこと**: クリティカルチェーンは

**なぜ必要か**: CCPM のクリティカルチェーンは**単なる最長経路ではなく、
資源（担当者）の競合も考慮**して求めます。画面側で正しく計算するのは簡単ではありません。

**（a）か（b）であってほしい**、という立場で確認してください。
（c）になる場合は、計算方法の取り決めが別途必要になり、実装量が大きく増えます。

入っている想定で書いています。

**影響範囲**: `UI-GANTT-03`、`UI-NET-02`。（b）なら API が 1 つ増えます。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **確定。サーバ側が決める。** 応答の `critical[]` にタスク id が並ぶ。画面側は計算しない。

## Q-016 日付と期間はどう表現されているか

**知りたいこと**:
- 日付の形式（`2026-04-01` か、別の形か）
- 期間の単位（日 / 時間 / 人日）
- **暦日か営業日か**（土日祝を飛ばして数えるか）
- 稼働カレンダー（休業日の定義）が計画ファイルに含まれるか

**なぜ必要か**: **暦日か営業日かで、ガントチャートの帯の長さが変わります。**
「10 日間」の帯が 10 日分なのか 14 日分なのかが変わるため、見た目に直結します。
また、期間から終了日を計算する場面でも必要です。

**分からない間の仮置き**: `<duration unit="day">` で営業日、
日付は `YYYY-MM-DD` 形式と想定しています。

**影響範囲**: `UI-GANTT-02`、`UI-GANTT-07`、データモデルの章。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **一部確定。** 日付は `YYYY-MM-DD`、期間は**日**（BM3 の分単位の値を `MinutesPerDay` で換算済み）。
> **暦日か営業日かは依然として不明。** 稼働カレンダーの情報も応答には無い。


> ✅ **2026-09-04 結論（利用者からの聞き取り 🟡）**
> 
> **期間は営業日、日付は西暦の `YYYY-MM-DD`。** 着手日を 1 日目と数え、土日を飛ばして完了日が決まる。
> 祝日・会社の休業日を除くのか、その情報がどこにあるかは別途 → `Q-041`。

## Q-002 サーバ側はどう起動し、どこで待ち受けるのか

**知りたいこと**:
- サーバ側は HTTP サーバか。ポート番号は固定か、可変か
- パスの前置き（`/api` など）はあるか
- 起動方法は。画面側はサーバ側が起動していることを前提にしてよいか
- **`GET /meta` のような「対応機能の一覧」を返せるか**

**なぜ必要か**: 画面側からの接続先が決まりません。
また、対応機能の一覧を返してもらえると、
**画面側が実行時に判定して、使えない機能を隠せます。**
サーバ側の版が上がって機能が増えたときも、画面側を直さずに済みます。

**分からない間の仮置き**: `http://127.0.0.1:8080/api/v1` としています。
`GET /meta` に `capabilities` を持たせる案を書いています。

**影響範囲**: `openapi.yaml` の `servers`、`GET /health`、`GET /meta`、
サーバ側に繋がらないときの案内文。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **一部確定。** API は**同一オリジン**の `/api/v1/*`。新 GUI は同じサーバの `/external/` に置かれるので、
> ホスト名・ポート番号を画面側が知る必要は無い。`GET /meta` は `server` `version` `capabilities[]` `writeEnabled` を返す。
> **`capabilities` の各名前の意味は不明**なので、画面側は `writeEnabled` だけを見る。起動方法は依然として不明。

# 中 — 実装方針に関わる

## Q-026 日程の再計算をサーバ側でできるか（保存はせずに）

**知りたいこと**: 期間や接続を変えたとき、後続タスクの日程・資源競合の解消・
バッファの再配置を**サーバ側が計算して返せる**か。
そのとき**ファイルには保存しない**ようにできるか。

**なぜ必要か**: CCPM の日程計算は資源競合まで絡むため、
画面側で再実装すると**二重持ちになり必ずズレます。**
ズレた絵を見て調整を判断されるほうが危険です。

一方で「入力しても絵が動かない」のは違和感があるので、
画面側は**いま編集した帯の長さだけ**を即座に反映し、
全体はサーバ側の答えで差し替える方針にしています。

**分からない間の仮置き**: サーバ側が計算できる前提。
打鍵のたびではなく、入力が落ち着いたら依頼します。

**影響範囲**: `UI-GANTT-11`、`UI-CONNECT-*`、API が 1 つ増える見込み。
以前の「編集中は通信しない」方針の見直しにあたります。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **未実装のまま。** 日程の再計算を返す呼び出しは無い。画面側は編集した帯だけを動かす方針を続ける。

## Q-027 選択肢から選ぶ項目はあるか

**知りたいこと**: 数十ある項目のうち、**値が決まった選択肢から選ぶもの**はあるか。
（例: 工程区分が `設計 / 実装 / 試験` からしか選ばない、など）

サーバ側が**項目の定義**（型・選択肢・ラベル・編集可否）を返せるか。

**なぜ必要か**: 素通し項目は意味を解釈しないため、**入力の助けが出せません。**
自由入力にすると表記ゆれや打ち間違いが入ります。

項目の定義を受け取れるなら、**素通しのままドロップダウンにできます。**
これは「項目が増えても仕様が増えない」を保ったまま使い勝手を上げる、
数少ない方法です。**交渉する価値が高い項目です。**

**分からない間の仮置き**: 一部の項目に選択肢がある前提でモックを作っています。

**影響範囲**: `UI-GANTT-11`、`UI-GANTT-18`、`GET /meta`。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）
> 
> **一部確定。** `priority` は `高` / `中` の 2 値（暫定表示）、`kind` は 3 値。他に選択肢を持つ項目は無い。

単位を取り違えると、消費 30% を 3000% として描くか、何も塗らないかになります。

**影響範囲**: `UI-GANTT-04`、`UI-NET-08`、[`interface/20-data-model.md`](interface/20-data-model.md)。

> **日数。** `duration` と同じ単位。モックはそのまま日数で描いている。

## Q-039 `assignees` は Skill 名。**人**はどこで分かるのか

**知りたいこと**: 受領した文書で `assignees` は「割当リソース名。BM3 Skill 名」とある。
例は `サウンドPAVCT`。

- リソース調整の対象は **Skill（資源の種類）でよいか**。それとも人まで落とす必要があるか
- 人の情報は BM3 のどこにあるか。応答に足せるか
- 1 つの Skill に何人いるか（容量）は分かるか

**なぜ必要か**: このツールの主目的は**リソースの調整**です。
画面は「リソース別」に並べ替えて重なりを見せ、調整パネルで別のリソースへ振ります。
その「リソース」が Skill なら、**「サウンドPAVCT が 5 月に 3 本重なっている」までは見えるが、
「その中の誰が」は見えません。** 会議の場でそれで足りるのかを確かめたい。

**分からない間の仮置き**: 画面では「担当」と呼んでいたものを**「リソース」**に言い換え、
Skill 名をそのまま並べています。判定はしない方針なので、Skill でも人でも画面の作りは同じです。

**影響範囲**: `UI-GANTT-27`〜`29`、`UI-NET-19`、`UI-ADJ-*`。人まで落とすなら `tasks[]` に項目が増えます。


> ✅ **2026-09-04 結論（利用者からの聞き取り 🟡）**
> 
> **Skill でよい**（利用者の決定）。リソース調整はこの粒度で行う。人まで落とす必要は無い。
> 画面の「リソース」は BM3 の Skill 名をそのまま並べる。

## Q-041 祝日・会社の休業日は営業日から除くのか

## Q-020 ネットワーク図の配置を覚える必要があるか

**知りたいこと**: 利用者が手で動かしたノードの位置を、次に開いたときも保つ必要があるか。

**なぜ必要か**: 保つ必要があるなら保存先を決めることになります。
**計画ファイルに座標を書き込むと、他のツールがそのファイルを読めなくなる恐れ**があるため、
慎重な判断が要ります。

**分からない間の仮置き**: **画面側だけで覚える。計画ファイルには書かない。**

> 🟡 **2026-08-29 追記** — 実際にノードを動かせるようにした結果、
> 自動配置が常に最適とは限らず、**手で直せることには価値がある**と分かった。
> 一方で計画ファイルに座標を書き込むのは避けたい（他のツールが読めなくなる恐れ）。
>
> そこで**画面側だけで覚える**ことにした。別のパソコンで開くと配置は自動に戻るが、
> 「整列」ボタンで自動配置に戻せる以上、大きな損失ではないと判断した。
>
> **残る確認事項**: 配置を持ち歩きたいという要望が実際にあるか。
> あるなら、計画ファイルとは別の場所（設定ファイルなど）に置く必要がある。

**影響範囲**: `UI-NET-05`、`UI-NET-10`。

> 読み仮名は無く、並び順の問題は同じ。「最初の作業が始まる順」を続ける。


> ✅ **2026-09-04 結論**（サーバ側の I/F 一覧を受領 — [`interface/received/`](interface/received/)）

## Q-007 アクセスの制限は必要か

**知りたいこと**: サーバ側は自分のパソコンからの接続だけを受け付ける作りになっているか。
認証の仕組みはあるか、必要か。

**なぜ必要か**: 利用者のパソコンの中だけで動く前提ですが、

**分からない間の仮置き**: 自分のパソコンからの接続のみ（`127.0.0.1`）を前提とし、
認証は設けていません。

**影響範囲**: `openapi.yaml` の `servers`、将来 AI 連携する場合の設計。

## Q-018 将来 AI から使う場合、何ができる必要があるか

**知りたいこと**: 「将来 AI に繋ぐ可能性がある」とのことだが、
