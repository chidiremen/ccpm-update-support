仕様の変更を記録します。**いつ・何を・なぜ**を残してください。

理由が書いてあれば、後から読む人が
「前提が変わったからこれは変えてよい」と自分で判断できます。

書き方:

```
## YYYY-MM-DD

### 変更した内容
- 何をどう変えたか

### なぜ
- どういう経緯・理由で変えたか（確認が取れた、方針が変わった、等）
```

### 設計上の判断

- **項目を中核と素通しに二分した。** タスクの項目は数十ある。
  全部を仕様に書き下すと、項目が増えるたびに仕様が腐る。

- **日程の再計算はサーバ側に一本化した。** CCPM の日程計算は資源競合まで絡み、
  画面側で再実装すると二重持ちになって必ずズレる。
  ただし「入力しても絵が動かない」違和感を避けるため、
  **いま編集した帯の長さだけ**は画面側で即座に反映する（計算ではなく入力の反映）。
  → 前回の「編集中は通信しない」を部分的に撤回
- **接続の UI をガントとネットワーク図で共通にした。** CCPM では接続が計画の本体。
  画面が変わるたびに操作を覚え直すのは無駄
- **接続はクリックでもドラッグでもできるようにした。** 人によって好みが分かれるため。
  相手が遠いときは一覧、近くに見えているときはドラッグが効く
- **マイルストン帯を固定表示にした。** スクロールで視界から消えると、
  「いま見ているタスクが納期に対してどの位置か」が分からなくなる

- 「編集場所を項目の性質で分ける」（値は表・つながりは図・その他はパネル）は**撤回**。
  慣れている道具に寄せることを優先し、**Excel 風の表を主戦場**にした。

## 2026-08-29 (3)

### 変更した内容

スマホから触ってもらった指摘への対応。**2 件はこちらの不具合**でした。

- **ネットワーク図のノードが回転する不具合を修正**（`mock/index.html`）
- **表とチャートの分割比率を指でも変えられるように**（`UI-GANTT-19`）
- **日 / 週 / 月で目盛りの粒度が実際に変わるように**（`UI-GANTT-20`）
- **変更内容のタブを廃止し、ガントとネットワーク図に重ねて表示**
  （`UI-DIFF-07` 濃淡 / `UI-DIFF-08` 見比べ）
- **日本語入力（IME）で編集が始まらない問題を修正**
- `docs/ui/13-diff.md` を全面的に書き直し
- `docs/ui/10-screens.md` `12-network.md` `14-navigation.md` を追随
- `docs/90-open-questions.md` に `Q-031` を追加

### 見つかった不具合とその原因

**1. ネットワーク図のノードが 45 度回転していた**

ガントのひし形用の CSS が `.milestone` という**限定なしのクラス名**だったため、
ネットワーク図の `<g class="net-node milestone">` にも当たっていた。
CSS の `transform` は SVG の `transform` 属性を上書きするため、
ノードが回転したうえ位置もずれていた。

→ `.bar-milestone` に改名。**クラス名は必ず親クラスで限定する**規約にそろえた。

**2. 分割の仕切りがタッチ環境で動かなかった**

マウスの押下だけを見ていたため、指では反応しなかった。

→ ポインタの入力として扱い、当たり判定を広げ、既定比率のボタンも足した。

**3. 日 / 週 / 月が拡大率しか変えていなかった**

目盛りは常に「月＋週」のままで、切り替えた実感がなかった。
選択中のボタンにも状態が出ていなかった。

**4. 日本語入力で編集が始まらなかった**

「打ち始めたら編集に入る」をキー入力の検知で作っていたが、
**日本語入力はキー入力の事象を発生させない。**
半角英数字では動くのに日本語では動かない、という状態だった。

→ 入力欄を常にカーソル位置のセルに重ねて置く方式に変更。
日本語の計画ファイルを扱う道具として、これは落とせない。

**5. 隠したはずのラベルが場所を取り、表とチャートの行が 24px ずれていた**

`display` を指定したクラスは、ブラウザ既定の `[hidden]{display:none}` に
勝ってしまう。`[hidden]` を必ず効かせる規則を足した。

### 設計上の判断

- **変更内容を独立した画面にしないことにした。**
  変更を確かめたい相手は帯や線そのもの。別画面に一覧を並べても、
  その変更が日程のどこに効くのかは分からない
- **「薄くする」を半透明の白ではなく不透明度で作った。**
  白い膜は明るいテーマでしか成立せず、暗いテーマだと
  薄くしたつもりのものが一番明るくなって逆転する
- **変更したセルの強調に塗りを使わない。**
  バッファ行など、もともと色が付いている行と見分けがつかなくなるため
- **保存衝突の解決に見比べ表示をそのまま使う。**
  衝突の解決も「変更前と変更後を見比べる」作業であり、専用画面は要らない

### なぜ

> Excel だけではなくさらに UI 追加したいです。
> **Excel もできるしこっちもできるというのが大切。**

キーボード操作しかない状態だった。
**細かい値を確実に入れたいときはキーボードが速く、
「この作業をここへ持っていく」はマウスのほうが速い。**
どちらか一方に寄せる理由がない。

ネットワーク図については「見づらい分かりづらい不便」という評価を受けた。

### ネットワーク図で分かったこと

**ドラッグできるようにするだけでは「見づらい」は解決しなかった。**
自動配置そのものに問題があった。

| 問題 | 直し方 |
|---|---|
| 段をまたぐ長い線が、途中のノードの上を突っ切る | **下へ迂回させる。これが最も効いた** |
| 同じ段の並び順が適当で線が交差する | つながっている相手の位置の平均に寄せて並べ替える |
| 名前が 10 文字で切れて何のタスクか分からない | 2 行に折り返す |
| 横に長すぎる | 段の間隔を詰める |

**測る指標を「線の交差の数」から「線がノードの上を通っている数」に変えた。**
交差の数では改善が数字に出なかった（各段のノードが少ないため）が、
実際の読みにくさは長い線がノードを突っ切ることが原因だった。
指標を変えたことで、直すべき場所がはっきりした。

### 設計上の判断

- **同じドラッグでも起点で意味を分ける。**
  ハンドルの上から始めたら「線をつなぐ」、ノード本体から始めたら「動かす」
- **縦の移動と横の移動で別のことをする。**
  行のドラッグは、縦で並び順、横で階層。1 回の操作で両方決まる
- **子孫は親についていく。** 親だけ動いて子が置き去りになると計画が壊れる
- **何も変わらなかったら履歴に積まない。** 積むと「元に戻す」が空振りする
- **手で動かした配置は計画ファイルに書かない。**
  他のツールがそのファイルを読めなくなる恐れがあるため

### 実装中に踏んだ不具合

- **掴んだ要素が再描画で DOM から外れていた。**
  ノードを掴んだ直後に選択状態を再描画していたため、
  掴んだ要素の参照が無効になっていた。掴むのを先にする順序へ変更
- **`pointerdown` で `preventDefault()` するとマウス互換イベントが発生しない。**
  接続のドラッグが `mousemove` を待っていたため、動かなくなっていた。
  ポインタの入力に揃えて解決
- **動かしたノードが他のノードの裏に隠れていた。**
  SVG は後に書いたものが前面に来るため、選択中と手動配置のノードを最後に描くようにした

**複数プロジェクトの表示とリソース調整。**
今回は「単プロジェクトの操作感が不便なままではプロジェクトを増やしても
使いものにならない」と判断して後回しにしました。

## 2026-08-29 (5)

### 変更した内容

**ネットワーク図に階層を導入しました。ガントの階層構造を「入れ子の枠」で表します。**

- `UI-NET-11` 親タスクが枠になり、その中に子の図が入る。何段でも入れ子にできる
- `UI-NET-12` 枠の見出しを掴むと、中身ごと動く
- `UI-NET-13` 枠を畳む・開く。**ガントの折りたたみと連動する**
- 枠をまたぐ線を、枠の縁を経由させるようにした
- サンプルデータを 3 階層にした（入れ子の中に入れ子がある形を試せるように）
- `docs/ui/12-network.md` / `10-screens.md` / `00-glossary.md` を更新

### なぜ

> 大分類がタスクかつグループ名のようになり、その中に中分類のネットワーク図表現が入る。
> これは折りたたんだりできる。中分類の中に小分類のネットワーク図が入り、
> これは折りたたむことができる。

これまでのネットワーク図は**階層を完全に無視して、葉タスクだけを平らに並べていた。**
親タスク（設計フェーズなど）は図に出てこなかった。

そのため「どの大分類の作業か」が図から読み取れず、
**畳んで小さくすることもできなかった。**
これが以前もらった「見づらい分かりづらい」の根本にあった。

### 設計上の判断

- **配置計算を再帰にした。** 枠の大きさは中身から決まるので、
  「すべてのノードが同じ大きさ」という前提は使えなくなった
- **段を決めるとき、依存を「その階層の代表」に読み替える。**
  枠の奥にある依存は、その階層では枠と枠の順序を意味する。
  読み替えないと枠の中と外で順序が食い違い、線が右から左へ戻る
- **線は葉から葉へ引く。** 枠の縁でまとめると、
  どのタスクからどのタスクへの依存か分からなくなる。
  ただし枠をまたぐときは枠の縁を経由させる（直線だと中身の上を横切るため）
- **折りたたみの状態はガントと共有する。**
  同じ計画を別の角度から見ている、という既存の方針に沿わせた
- **手で動かした位置は「枠の中でのずれ」として持つ。**
  絶対位置にすると、親の枠が動いたとき中身が置き去りになる
- **枠は見出しを掴んだときだけ動かす。**
  枠の中の余白で枠ごと動くと、中のノードを狙えなくなる
- **枠の濃淡は「地の色にどう重ねるか」で表す。**
  単純に不透明度を下げると、暗いテーマで枠が地に沈んで見えなくなる

### 測り方について

**描画と計測を同じ経路の計算に統一した。**
別々に持っていると「直したつもりで計測だけ良くなる」ことが起きる。

この統一のおかげで、**枠から出る線が同じ枠の中の後ろのタスクの上を通る**という
見落としが見つかった。目で見ただけでは気づきにくい種類の問題だった。

### 実装中に踏んだ不具合

- **行を真横にずらすだけでは階層が変わらなかった。**
  落とし先が自分自身の位置になるため「動かしていない」と判断して
  処理を打ち切っていた。動かしている塊の次の行を目印にするよう修正

> 編集できるパラメータは後ほどバックエンド側のエンジニアに編集を任せるので

「あとで別の人が項目をいじる」という前提が入った。
これは**項目定義を 1 か所に集めて、そこを直せば画面が全部追従する**構造にせよ、

### 設計上の判断

- **設計書をモックとは別に置いた。**
  サーバ側のエンジニアに「モックの JavaScript を読んで直して」とは言えない。
  `24-field-catalog.md` が受け渡し物で、モックの `FIELDS` はその写し
- **食い違いを機械で検出するようにした。**
  文書とコードの二重管理は必ずズレる。`check-spec.sh` が両者の項目を突き合わせる。
  ズレたら手順を案内して落ちる
- **親子の変更と位置の移動を、同じドラッグで扱う。**
  入れ子の道具では「どこに置いたか」がそのまま所属を意味するのが自然で、
  別の操作を覚える必要がない
- **並び順の正規化を 1 つの関数に集約した。**
  ネットワーク図からでもガントの行ドラッグからでも、同じ処理を通す
- **足したタスクはすぐ編集画面を開く。**
  名前が「新しいタスク」のまま図に残ると、何の作業か分からなくなる
- **迷ったら素通し項目にする**、という判断基準を設計書に書いた。
  中核にすると仕様が増え、合わせ込みの対象も増えるため

### 実装中に踏んだ不具合

- **掴んでいるノード自身がカーソルの下にいて、落とし先を自分だと誤判定していた。**
  ドラッグ中は本人を当たり判定から外すようにした
- **`pointerdown` で既定動作を止めると `dblclick` が発生しない。**
  以前マウス互換イベントで踏んだのと同じ罠。ダブルクリックを自前で判定するようにした

### 検証で確かめていること

**「項目定義に 1 行足すと、表の列にもダイアログにも自動で現れる」**を
自動検証に入れた。ここが通れば、あとで人に任せられる構造になっている証明になる。

  **一覧の先頭に「（最上位 — 親なし）」**
- `UI-NET-16` ネットワーク図に「親を変更…」「|← 親から出す」ボタン
- `UI-NET-17` ドラッグ中に、何が起きるかを**言葉で**出す札
- ヒント文に「余白に落とすと最上位に出ます」を併記

### なぜ

> どうやってネットワーク図上から子供にするの？
> また、子供の状態から他人にするにはどうすればいい

**作った本人が訊かないと分からない、という時点で作りが悪い。**
機能はあったが、見つけられなかった。

欠けていたのは 3 つ:

1. **「親から出す」方法がどこにも書いていなかった。**
   ヒントは「子にする」しか触れていなかった
2. **ドラッグ中の合図が色だけだった。** 緑と赤の縁取りしかなく、
   何が起きるのかが言葉で出ていなかった
3. **マウスでしかできなかった。**
   ガントには「→| 下げる」「|← 上げる」があるのに、ネットワーク図には無い。
   **「Excel もできるしこっちもできる」という要件が、ここだけ守れていなかった**

### 設計上の判断

- **親子関係を「編集できる項目」の一つにした。**
  いちばん確実で探さなくても見つかる置き場所は、既にある編集画面。
  項目定義に 1 行足すだけで載るので、既存の構造がそのまま効いた
- **一覧の先頭に「最上位」を置いた。** ここに出ていないと、
  「親から出す」方法が画面のどこにも見当たらない状態が続く
- **札に言葉を出した。** 色だけでは「緑＝いいこと」までしか伝わらない

### 実装中に見つけた不具合

- **編集画面から一覧を開くと、ポップアップが画面の左上に出てタブを覆っていた。**
  ダイアログを閉じてから位置の基準にしていたため、
  基準の要素が既に DOM から外れており、座標がすべて 0 になっていた。
  **閉じる前に矩形を取っておく**ように修正
- **ドラッグ中に図全体が再配置され、狙いが定まらなかった。**
  動かすたびに枠の大きさが変わり、周りが動いていた。
  **掴んでいる間は掴んだノードだけを動かし、確定は離したときだけ**に変更

### なぜ

このツールを作る動機の中心がここにあるため。

> 追加要件、一番キモとなるのは、複数プロジェクトをいかに見やすく表示するか、
> になります。**主目的はリソースの調整**ですので。

1 つの計画を直すだけならガントチャートで足りる。
現場で本当に困るのは、**同じ人が複数の計画に同時に呼ばれている**こと。

### 設計上の判断

**1. 判定しない。見えるようにする。**

以前この話が出たとき、こちらが資源の競合の自動判定まで作ろうとして止められた。

> そんなリクエストしたっけ
> そんなもん決まってません。**そんながちがちに管理できたら苦労しません**

現場の調整はルールでは決まらない。
「重なっているから 3 日ずらす」を機械が決めても、
**その 3 日をずらしてよいかは機械には分からない。**

そこで、次のものは**作らないと決めた**。

- 資源の競合の自動判定・警告
- 優先度による自動整列
- **負荷のグラフ**（誰がいつ何 % 埋まっているか）

**2. 負荷のグラフを作らなかった理由。**

描くには**工数と割当率**が要るが、あるかどうか未確認（→ `Q-034`）。
いま分かっているのは期間（何日間か）だけで、それだけで描くと

- 1 日 1 時間だけ関わる 20 日のタスク
- 20 日間つきっきりのタスク

が**同じ高さの棒**になる。事実と違うものを事実の顔で見せることになるので作らない。

**3. リソース調整の本体は「担当者別の並べ方」。**

**プロジェクト別の表をいくら眺めても、
「佐藤さんが 5 月に 3 つのプロジェクトで取り合いになっている」は見えない。**
その人の作業が 3 つの離れた場所に散らばっているため。
行を人に変えて、ひとつの時間軸に並べて初めて見える。重なりは見れば分かる。

**4. 行の作り替えは最小限にした。**

`rows()` は 30 か所から使われ、タスクの識別子は 130 か所以上に出てくる。
全面的な作り替えは割に合わない。

そこで `rows()` の戻り値は**今まで通りタスクの配列**のままにし、
見出し行（プロジェクト名・担当者名）を**作り物の行**として混ぜる形にした。
描画側は 2 つの目印を見るだけで済んでいる。

**5. 担当者別では、同じタスクが複数の人の下に出る。**

1 つのタスクに複数人いるため。
「佐藤さんの予定」を見たいときに「そのタスクは田中さんの欄にあります」
と言われても役に立たない。**どちらの人の欄からも見えることが正しい**と判断した。

選択は行番号で持っているので、同じタスクが 2 回出ても壊れない。

**6. 担当者別では、並べ替えと階層の操作を効かなくした。**

人の下の並びには意味がない（日程順に並べているだけ）。
そこに行を挿したり階層を作ったりできると、何が起きたのか説明できなくなる。
**ボタンも押せない見た目にした。押せるのにできないのは嘘になる。**
セルの編集はできる（出ているのは同じタスクの実体そのもの）。

**7. プロジェクトの色は「行の左端の帯」に置いた。**

帯の塗りと枠線は、すでにクリティカルチェーンと種別が使っている。
そこへ重ねると**同じ場所が 2 つの意味を持ち**、どちらの話なのか読み取れなくなる。

**8. ネットワーク図は、枠を 1 段外に足しただけ。**

入れ子の枠はすでにあるので、
畳む・広げる・中身ごと動かすがそのまま効いた。**新しい仕組みを増やしていない。**
中のノードには色帯を付けない — どのプロジェクトかは外側の枠が示しており、
同じことを 2 か所で言うと、かえって何の印なのか分からなくなるため。

**9. 担当を素通しから中核へ移した。**

判断基準（「この項目がないと絵が描けなくなるか」）は変えていない。
**画面が変わったので答えが変わった。**
担当者別に並べる機能を作った時点で、担当は「行を作るのに要る項目」になった。

`Q-030` に「リソース調整をやるなら資源も中核に要る」と書いていた点が、ここで現実になった。

**10. API は増やしていない。**

並べ替えと絞り込みは、すでに受け取っているデータの中だけで済む。

⚠️ ただし**プロジェクトごとに計画ファイルが分かれている場合は、
複数のファイルを同時に開く必要が出る**（→ `Q-035`）。
**どちらになるか分からないうちは API を先に決めない。**
決め打ちで作ると、外れたときに画面側まで巻き込んで直すことになる。
画面仕様は**どちらでも変わらない**書き方にしてある。

### 実装中に見つけたこと

- **ネットワーク図の最上位の枠が段違いに見えた。**
  段の中でノードを中央揃えにしていたため、幅の違うプロジェクトの枠がずれていた。
  **いちばん外側の枠だけ左揃え**にした
- **担当者の並び順が決められなかった。**
  漢字の名前をそのまま並べても五十音順にはならない。
  読み仮名を持っていないため（→ `Q-036`）、
  **最初の作業が始まる順**にした。右のガントの流れと同じ向きに読める

- `UI-GANTT-28` **担当者別で、行を別の人の欄へ落とす＝担当の付け替え。**

- `UI-NET-19` ネットワーク図で**担当者で強調**（その人の作業がプロジェクトをまたいで浮き上がる）
- 既定の列順で、担当をタスク名の隣へ

### なぜ

> ここまでで、「こんなことできたら改善できそうなのにな」というのがもしあれば織り込んで

前回の対応で「見える」ようにはなったが、**見えたあとに動かす手段**がセルの打ち直ししかなかった。
リソースの調整とは結局「この作業を誰に持ってもらうか」を決めることなので、
表を見ながらそのまま動かせるようにした。

人が増えたときの眺め方（まとめ行の帯・絞り込み）と、
ネットワーク図側で人の話ができないこと（強調）も、同じ理由で足した。

### 設計上の判断

- **判定しない、の線は越えていない。** 足したのはすべて「見える」か「動かす手段」。
  負荷の %、空き時間の算出、重なりの件数表示は引き続き作らない
- **まとめ行の帯は負荷のグラフではない。** 同じ帯を 1 行に描いているだけで、
  数値も判定も足していない。重なりは重なって見える、それだけ
- **ドラッグは「移す」であって「加える」ではない。**
  2 つの意味を持たせると、どちらになったのか落とすまで分からない。
  掛け持ちを増やすときはセルか編集画面で書き足す
- **すでにその人が担当なら断る。** 黙って何もしないと「効かなかった」と思われる。
  札に「すでに『山本』の担当です」と出す

### 実装中に見つけた不具合

- **選択肢のセル（種別など）を Enter で閉じると落ちていた。**
  要素を取り除く途中で blur が飛んできて閉じる処理に二重に入り、
  取り除き済みの要素をまた取り除こうとしていた。閉じるのは 1 回だけにした
