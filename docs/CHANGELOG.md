# 変更履歴

仕様の変更を記録します。**いつ・何を・なぜ**を残してください。

理由が書いてあれば、後から読む人が
「前提が変わったからこれは変えてよい」と自分で判断できます。

書き方:

```
## YYYY-MM-DD

### 変更した内容
- 何をどう変えたか

### なぜ
- どういう経緯・理由で変えたか（確認が取れた、方針が変わった、等）
```

### なぜ

サーバ側は実装済みだが、**その I/F 仕様が現時点で入手できていない**ため。

後から実物に合わせ込むことを前提に、
「差し替えやすい器」を先に作った。具体的には:

- **確定度マーカー**（🟢🟡🔴）で、確定した事実と推測を混ぜないようにした<!--legend-->
- **確認事項に ID を振り**、社内で聞くべきことを 1 ページに集約した
- **仕様の正を二層に分けた**（API の表面 / データの中身）。
  実物と違ったとき、直す場所が分かれるようにするため
- **操作 ID で画面と API を対応付けた**。
  実物と違ったとき、どの画面が影響を受けるか分かるようにするため

### 設計上の判断

- **画面仕様を API 仕様より先に書いた。**
  当初は API から書こうとしたが、どんな画面があるか決まらないと
  必要な API は決められないため、順序を入れ替えた
- **保存時の版の照合（`If-Match`）を最初から入れた。**
  XML 全文を置き換える設計では、対策がないと
  後から保存した人が前の人の変更を消す。
  後から足すのは画面側とサーバ側の両方の改修になるため、初手で入れた
- **略語を本文で使わないことにした。**
  「初見でも分かるように」という要件に対し、
  `FE` `BE` のような略語は読み手を止めるため
