# データモデル（計画ファイルの構造）

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。

## ⚠️ この章の全体が推測です

**実物の計画ファイルをまだ入手できていません**（→ `Q-001`）。

この章に書かれた要素名・属性名は、**すべてこちら側が仮に置いたもの**です。
実物とは違う可能性が高いと考えてください。

**この章は差し替え前提で作られています。**
実ファイルを 1 つ入手できれば、この章を書き換えるだけで済むよう、
他の章はここへの参照だけを持つ形にしてあります。

---

## 二層構造の考え方

このリポジトリでは、仕様の「正」を 2 つに分けています。

| 層 | 何を決めるか | 正となるファイル |
|---|---|---|
| **API の表面** | どこに何を送ると、何が返るか | [`openapi.yaml`](openapi.yaml) |
| **データの中身** | 計画ファイルの要素・属性・値 | **この章** |

分けている理由は、**後日サーバ側の実物に合わせ込むとき、修正箇所を切り分けるため**です。

「API の形が違った」のか「XML の中身が違った」のかで直す場所が分かれ、
片方の修正がもう片方を壊しません。

XML を扱うからといって OpenAPI が使えないわけではありません。
OpenAPI は XML 形式のやり取りを普通に表現できます。

---

## XML を API でどう包むか 🔴推測 (`Q-003`)

計画の中身は **XML 文字列そのもの**をやり取りします。
問題は、それを**どういう形で運ぶか**です。2 案あります。

### 案 A: JSON の中に入れる（**初版の採用案**）

```json
{
  "planId": "pln_01HZX3K8",
  "revision": "r7",
  "sourcePath": "C:\\work\\project-a.xml",
  "xml": "<?xml version=\"1.0\"?><plan>...</plan>"
}
```

**採用理由**: `revision` などの付帯情報を**一緒に運べる**ためです。

`revision` は保存衝突を防ぐのに必須で（[`../01-overview.md`](../01-overview.md) 参照）、
XML と必ずセットで扱う必要があります。JSON に入れておけば取り違えが起きません。

**欠点**: XML が文字列として入るため、引用符などの記号が
エスケープされて読みにくくなります。また、わずかにデータ量が増えます。

### 案 B: XML をそのまま本文にする

```
HTTP/1.1 200 OK
Content-Type: application/xml
ETag: "r7"

<?xml version="1.0"?><plan>...</plan>
```

**利点**: 素直。ブラウザや既存のツールでそのまま見られます。

**欠点**: `revision` を HTTP ヘッダー（`ETag`）で運ぶことになり、
本文と別々に扱う必要があります。付帯情報が増えると窮屈になります。

### 判断

⚠️ **サーバ側がすでにどちらかで作られている可能性が高いため、これは確認事項です**（→ `Q-003`）。

サーバ側が案 B で実装済みなら、そちらに合わせます。
`openapi.yaml` では**両方を書ける形にしてあり**、片方を消せば済むようにしています。

## 項目を二分する — 中核項目と素通し項目 🟡暫定 (`Q-030`)

**タスクに紐づく項目は数十あります。** 固定のセットがあるとのことです。

これを仕様に全部書き下すのは無理があり、項目が増えるたびに仕様が腐ります。
そこで**役割で二分**します。

| 区分 | 意味 | I/F 仕様に書くか |
|---|---|:---:|
| **中核項目** | 画面側が**意味を理解して使う**。ガントやネットワーク図を描くのに必要 | **書く** |
| **素通し項目** | 表示・編集はできるが、**ツールは意味を解釈しない**。読んだまま持ち回り、保存時にそのまま書き戻す | **書かない** |

### 中核項目の一覧 🔴推測 (`Q-030`)

| 項目 | なぜ意味を理解する必要があるか |
|---|---|
| 識別子 | 行やノードを指し示すのに要る |
| 名称 | 表示に要る |
| 種別（タスク / マイルストン / バッファ） | 描き分けに要る |
| 期間・着手日・完了日 | **帯の位置と長さを決める** |
| 先行 / 後続の接続 | 依存線とネットワーク図の骨格 |
| 階層（親子） | 折りたたみと集計に要る |
| 進捗 | 帯の中の塗り分けに要る |
| バッファの大きさ・消費量 | バッファの見せ方に要る |
| クリティカルチェーン | 強調表示に要る |

⚠️ **この一覧に抜けがないかは要確認です**（→ `Q-030`）。
「画面側が意味を理解しないと困る」項目が他にあれば、中核に移します。

### なぜこう分けるのか

**1. I/F 仕様が項目数に引きずられない。**
素通し項目が 20 個でも 200 個でも、仕様に書くのは中核項目だけ。
サーバ側が項目を増やしても、画面側は無改修で列が増えます。

**2. 知らない項目を落とさない。**
XML を全文やり取りする設計が、ここで効きます。
ツールが理解できない要素も原文のまま残るため、
**未対応の項目があってもファイルが壊れません。**

**3. 実物と違ったときの直し方が分かれる。**
中核項目の名前が違った → 読み替え表を直す。
素通し項目が増えた → 何もしなくてよい。

### 素通し扱いの弱点 🔴推測 (`Q-027`)

⚠️ 意味を解釈しないということは、**入力の助けが出せない**ということです。

たとえば「工程区分」が `設計 / 実装 / 試験` からしか選ばないものだとしても、
素通しなら自由入力になり、**表記ゆれや打ち間違いが入ります。**

選択肢を持つ項目があるなら、その情報だけは受け取りたい（→ `Q-027`）。
サーバ側が項目の定義（型・選択肢・ラベル）を返せるなら、
**素通しのまま入力の助けが出せます。**

## 計画ファイルの構造 🔴推測 (`Q-001`)

以下は**完全な仮置き**です。実物を見て差し替えます。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<plan schemaVersion="1.0">

  <!-- 計画全体の情報 -->
  <project>
    <name>プロジェクト A</name>
    <startDate>2026-04-01</startDate>
    <calendar>businessDays</calendar>   <!-- Q-016: 暦日か営業日か -->
  </project>

  <!-- タスクの一覧。入れ子で階層を表す想定 (Q-008) -->
  <tasks>
    <task id="T001" name="設計フェーズ">
      <task id="T002" name="要件定義">
        <duration unit="day">8</duration>       <!-- Q-016: 単位 -->
        <start>2026-04-01</start>
        <finish>2026-04-10</finish>
        <assignee>佐藤</assignee>
        <progress>100</progress>                <!-- Q-019: 実績は対象か -->
      </task>
      <task id="T003" name="基本設計">
        <duration unit="day">12</duration>
        <assignee>鈴木</assignee>
      </task>
    </task>
  </tasks>

  <!-- 依存関係 (Q-009) -->
  <dependencies>
    <dependency from="T002" to="T003" type="FS" lag="0"/>
  </dependencies>

  <!-- バッファ (Q-010) -->
  <buffers>
    <buffer id="B001" kind="project" size="10" unit="day" consumed="3"/>
    <buffer id="B002" kind="feeding" size="4" unit="day" protects="T003"/>
  </buffers>

  <!-- クリティカルチェーン (Q-011: サーバ側が計算するか) -->
  <criticalChain>
    <taskRef id="T002"/>
    <taskRef id="T003"/>
  </criticalChain>

</plan>
```

### 各部分の未確定点

| 部分 | 確認したいこと | ID |
|---|---|:---:|
| タスクの階層 | 入れ子か、親 ID を持つ平坦な一覧か、そもそも階層がないか | `Q-008` |
| 期間の単位 | 日か時間か。暦日か営業日か。稼働カレンダーはあるか | `Q-016` |
| 依存関係 | 4 種類（FS/SS/FF/SF）を表現できるか。遅延（lag）はあるか | `Q-009` |
| バッファ | 専用の要素か、特別なタスクか、属性か | `Q-010` |
| クリティカルチェーン | ファイルに入っているか、計算が必要か | `Q-011` |
| 実績・進捗 | このツールの対象か | `Q-019` |
| 文字コード | UTF-8 固定か、Shift_JIS もあり得るか | `Q-017` |
| 規模 | タスク数の想定上限 | `Q-012` |

## 画面側での扱い

画面側は、受け取った XML を**画面表示用の形に読み替えて**使います。

```
XML 文字列
   ↓ 解釈する
画面表示用の形（タスクの一覧、依存の一覧、バッファの一覧）
   ↓ ガント／ネットワーク図で表示
   ↓ 利用者が編集する
   ↓ 書き出す
XML 文字列（保存用）
```

### 読み替えの表を 1 か所にまとめる

**XML の要素名を画面のあちこちに散らばらせない**のが重要です。

「`<duration>` という要素から期間を取る」という知識を 1 か所に集約しておけば、
実物の要素名が違ったときに、**そのファイルだけを直せば済みます。**

```
XML                                 画面側
────────────────────────────────────────────────────
<task id="...">                 →   識別子              [中核]
  <name>                        →   名称                [中核]
  <duration unit="day">         →   期間（日数に換算）   [中核]
  <start> / <finish>            →   着手日 / 完了日      [中核]
  <progress>                    →   進捗                [中核]
  入れ子 / parentId             →   階層                [中核]
<dependency from= to= type=>    →   先行 / 後続の接続    [中核]
<buffer kind="project">         →   プロジェクトバッファ [中核]
<buffer kind="feeding">         →   合流バッファ        [中核]
<buffer kind="milestone">       →   マイルストンバッファ [中核] (Q-028)
<milestone> もしくは duration=0 →   マイルストン        [中核] (Q-028)
<criticalChain>                 →   クリティカルチェーン [中核]

上記以外のすべての要素・属性     →   素通し（意味を解釈しない）
```

**「上記以外はすべて素通し」と書けることが重要です。**
実物にどんな項目があっても、この表に載っていないものは
画面側が触らずに保持します。

⚠️ **書き出すときは、元の書式をできるだけ保ちます。**
1 か所直しただけで、属性の順序や改行がファイル全体で変わってしまうと、
利用者が不安になり、他のツールとの差分も読めなくなります（→ `Q-023`、
[`../ui/13-diff.md`](../ui/13-diff.md) の `UI-DIFF-04` 参照）。
