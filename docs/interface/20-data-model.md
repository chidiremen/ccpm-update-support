# データモデル — `GET /portfolio` が返す計画の中身

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。

## この章の現在の状態

**2026-09-04 にサーバ側の I/F 一覧を受領し、書き直しました。**
原文は [`received/2026-09-04-frontend-interface-list.md`](received/2026-09-04-frontend-interface-list.md)。

以前のこの章は「XML の要素がどうなっているか」の推測でした。
**画面側は XML を一切見ないことが分かった**ので、その話は無くなりました。
サーバ側が BM3 の XML を解析し、画面が扱いやすい JSON に変換して返します。

## 二層構造の考え方（変わらない部分）

| 層 | 何を決めるか | 正 |
|---|---|---|
| API の表面 | どこに何を送ると何が返るか | [`openapi.yaml`](openapi.yaml) |
| データの中身 | **返ってくる JSON の各項目の意味** | この章 |

以前は「データの中身 = XML の要素」でしたが、いまは「= JSON の項目」です。
分ける理由は変わりません。**API の形が違ったのか、中身の意味が違ったのか**で直す場所が分かれ、
片方の修正がもう片方を壊しません。

**XML の要素名は、画面側のどこにも出てきません。** 変換はサーバ側の仕事です。
この設計目標は、サーバ側が JSON で返してくれることで自動的に達成されました。

## 応答の全体 🟢

```
Portfolio
├── planId      いまは常に "bm3-portfolio"
├── revision    版の印。将来の保存で使う。読んだら保持する
├── sourcePath  サーバ側が読んだ場所（表示用）
├── projects[]  プロジェクト（id, name, color）
├── tasks[]     タスク・マイルストン・バッファのすべて
├── deps[]      依存関係（from, to）
├── critical[]  クリティカルチェーン上のタスク id
├── today       判定基準日
└── errors[]    読めなかったプロジェクト（空なら正常）
```

### 識別子の決まり 🟢

- タスクの `id` は **`{ProjectId}:{TaskId}`**（例 `17:194`）
- **画面側で作り替えてはならない。** `deps[]` と `critical[]` はこの `id` で結ばれている
- `parentId` も同じ形。最上位は `null`
- プロジェクトの `id` は BM3 の ProjectId（例 `17`）

> モックでは読みやすさのために `T002` のような短い id を使っていますが、
> 実物は上の形です。モックはあくまで画面の形を確かめるためのものです。

### 複数プロジェクト 🟢

**1 回の呼び出しで複数のプロジェクトが返ります。** タスクは `projectId` でどのプロジェクトのものか分かります。
プロジェクトの**色はサーバ側が決めて `color` で返します**（画面側で割り当てません）。

以前は「ファイルが分かれているなら複数を開く必要がある」と心配していましたが、不要になりました（`Q-035` ✅）。

## 項目を二分する — 中核項目と素通し項目 🟢

| 区分 | 意味 |
|---|---|
| **中核項目** | 画面側が**意味を理解して使う**。ガントやネットワーク図を描く・並べ替えるのに必要 |
| **素通し項目** | 表示・編集はできるが、**ツールは意味を解釈しない** |

**項目の一覧そのものは [`24-field-catalog.md`](24-field-catalog.md) にあります。**
以前は「数十項目ある」という前提で仮の一覧を置いていましたが、実物は下の通りで、**思ったより少ない**です。

### `tasks[]` の項目と画面側での扱い 🟢

| JSON の項目 | 区分 | 画面側での扱い | 備考 |
|---|:---:|---|---|
| `id` | 中核 | 行・ノードの識別子。**作り替えない** | |
| `projectId` | 中核 | 色分け・絞り込み・プロジェクト別の並べ方 | |
| `name` | 中核 | 表示 | |
| `kind` | 中核 | 描き分け（`task` / `milestone` / `buffer`） | **判定は暫定**（サーバ側の文書より） |
| `parentId` | 中核 | 階層・折りたたみ・入れ子の枠 | |
| `duration` | 中核 | 帯の長さ。単位は**日** | 分単位の値を `MinutesPerDay` で換算済み |
| `start` / `finish` | 中核 | 帯の位置。`YYYY-MM-DD` | 暦日か営業日かは未確認 (`Q-016`) |
| `progress` | 中核 | 帯の中の塗り | **暫定値**。BM3 の正式な進捗率ではない |
| `assignees` | 中核 | **リソース別の並べ方・調整パネル** | **BM3 の Skill 名。人の名前ではない** (`Q-039`) |
| `consumed` | 中核 | バッファの消費の見せ方 | `kind=buffer` のみ。**単位が未確認** (`Q-038`) |
| `protects` | 中核 | バッファが守る相手 | `kind=buffer` のみ。現時点は DependencyId |
| `wbsCode` | 素通し | 表示・編集 | BM3 の Task Code |
| `priority` | 素通し | 表示・編集 | **暫定表示**（クリティカルなら `高`、それ以外 `中`） |
| `phase` | 素通し | 表示・編集 | 現時点は常に空 |
| `note` | 素通し | 表示・編集 | BM3 の Memo、またはバッファの情報 |
| `createdAt` / `updatedAt` | 素通し（編集不可） | 表示 | **プロジェクトの AsOfDate 由来**。タスク個別の値ではない |
| `sourceProjectId` / `sourceTaskId` / `sourceBufferId` | 素通し（編集不可） | 表示 | 元の BM3 上の識別子。突き合わせ用 |

`deps[]` から画面側が作る項目（JSON には無い）:

| 画面の項目 | 作り方 |
|---|---|
| 先行タスク | `deps[].to === 自分` の `from` |
| 後続タスク | `deps[].from === 自分` の `to` |
| 親タスク | `parentId` を名前で表示 |
| プロジェクト | `projectId` を名前で表示 |

### 無くなった項目

以前の仮の一覧にあって、実物に無いもの: 部署・承認者・作業場所・使用設備・レビュー・版数・タグ・
費用コード・外注先・契約番号・顧客・成果物・見積根拠・リスク。
**画面側の項目定義からも消しました**（[`24-field-catalog.md`](24-field-catalog.md)）。

「素通しなら何個増えても仕様は増えない」という考え方は残しています。
サーバ側が将来 `tasks[]` に項目を足したら、項目定義に 1 行足すだけで表と編集画面に出ます。

## 依存関係 🟢

```json
{ "from": "17:194", "to": "17:159" }
```

**種類（終了→開始など）と遅延の指定はありません。** 終了→開始のみと読みます（`Q-009` ✅）。
以前の想定にあった `type` `lag` は消しました。

---

## バッファとマイルストン 🟢

- バッファは**独立した要素ではなく、`tasks[]` に `kind=buffer` として混ざって**返ります。元は BM3 の `MilestoneBuffer`
- バッファ行は `sourceTaskId` を持たないことがあり、代わりに `sourceBufferId` を持つ
- `consumed` が消費の度合い、`protects` が守る相手（DependencyId）
- マイルストンは `kind=milestone`。判定は「期間ゼロ」からの推定（暫定）

画面側の「マイルストン帯」（`UI-GANTT-17`）と「バッファの帯」（`UI-GANTT-04`）は、
`kind` を見て描き分けます。変換の心配はありません（`Q-010` `Q-028` ✅）。

⚠️ `consumed` が **0〜1 なのか 0〜100 なのか、日数なのか**が分かりません（`Q-038`）。
モックは仮に「日数」で描いています。

---

## クリティカルチェーン 🟢

`critical[]` にタスクの `id` が並びます。**サーバ側が決めます。** 画面側は計算しません（`Q-011` ✅）。

---

## 「今日」 🟢

`today` が判定基準日です。起動クエリの `asOf` を反映した値になります。
画面の「今日」の線はこれを使い、**画面側の時計を使いません**（会議で「先週時点の絵」を見せるときに必要）。

---

## 読めなかったプロジェクト 🟢

```json
"errors": [ { "projectId": "99", "message": "No XML file found ..." } ]
```

空でなければ、そのプロジェクトのタスクは応答に**含まれていません**。
画面側は必ず利用者に伝えます（`UI-COMMON-11`、[`22-errors.md`](22-errors.md)）。

---

## 画面側での扱い

```
GET /portfolio の JSON
   ↓ そのまま内部状態へ（id を変えない）
画面表示用の形（タスクの一覧、依存の一覧、クリティカルの集合、revision）
   ↓ ガント／ネットワーク図／調整パネルで表示
   ↓ 利用者が編集する（画面内ドラフト）
   ↓ writeEnabled が true になったら保存 I/F へ（未実装）
```

サーバ側の文書にある最小の接続例をそのまま引きます。**これが読み替え表のすべてです。**

```js
projects = data.projects;
tasks    = data.tasks;
deps     = data.deps;
critical = new Set(data.critical);
revision = data.revision;
```
