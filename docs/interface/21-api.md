# API の解説 — 画面側とサーバ側のやり取り

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。
> **正は [`openapi.yaml`](openapi.yaml) です。** この章は読み物としての解説版で、食い違いがあれば `openapi.yaml` が優先します。

## この章の現在の状態

**2026-09-04 にサーバ側の I/F 一覧を受領しました。**
原文は [`received/2026-09-04-frontend-interface-list.md`](received/2026-09-04-frontend-interface-list.md) にあります。

それまでの内容は**ほぼすべてこちらの推測**でしたが、読み込み側は実物に差し替えました。
書き込み側（保存・検証）は**サーバ側で未実装と明記されている**ため、
こちらの想定を叩き台として残し、🔴 のままにしています。

## いちばん大きく変わったこと

| 以前の想定 | 実物 |
|---|---|
| 計画ファイルを**パスで指定して開く**（`POST /plans`） | **開く操作は無い。** サーバ側が自分の置き場所の XML を読む。画面側は**プロジェクトの識別子**を渡すだけ |
| 計画の中身は **XML 文字列**で受け取る | **サーバ側が JSON に変換して返す。** 画面側は XML の要素名を一切知らなくてよい |
| 1 回の呼び出しで 1 つの計画 | **複数のプロジェクトを 1 回で**受け取る（`projectIds=17,49`） |
| 保存・検証の API がある前提 | **未実装。** `writeEnabled=false` の間、画面側はサーバ側へ保存しない |
| 担当は人の名前 | **BM3 の Skill 名**（資源の種類）。人の名前ではない (`Q-039`) |

> **「XML の要素名を画面側に散らばらせない」という設計目標は、サーバ側が JSON に変換してくれることで
> 自動的に達成されました。** 画面側の読み替え表は [`20-data-model.md`](20-data-model.md) にありますが、
> XML の話は出てきません。

## 一覧

| メソッド | パス | 用途 | 由来する画面操作 | 確定度 |
|---|---|---|---|:---:|
| `GET` | `/health` | 疎通確認 | 起動時 | 🟢 |
| `GET` | `/meta` | サーバ側の版と**書き込み可否** | 起動時 `UI-DIFF-09` | 🟢 |
| `GET` | `/portfolio` | **複数プロジェクトの計画を読む（主たる API）** | 起動時 `UI-COMMON-10` ガント・ネットワーク図・調整パネルの全操作 | 🟢 |

すべて**同一オリジン**の `/api/v1` の下にあります。新 GUI はこのサーバの `/external/` から配信されるので、
ホスト名やポート番号を画面側が知る必要はありません。

### 無くなったもの

以前の想定にあって、実物に無いことが分かったものです。

| 以前 | なぜ無くなったか |
|---|---|
| `POST /plans`（開く） | 開く操作そのものが無い。サーバ側が自分の置き場所を読む |
| `GET /plans/{planId}`（XML 取得） | `GET /portfolio` に置き換わった |
| `POST /plans/{planId}/save` | 保存 I/F 自体が未実装。`PUT` と分ける必要があるかも含めて未定 |
| `DELETE /plans/{planId}`（セッションを閉じる） | セッションという概念が無い |

### 既存の PoC 用 API

サーバ側の文書には、既存のトップ画面（進捗会議マトリクス）用の API も列挙されています
（`GET /api/matrix` `GET /api/selection` `GET /api/impact` `GET /api/skills` `GET|PUT /api/config/function-teams`）。
**新 GUI はこれらを使いません。** サーバ側の文書にも「新 GUI の通常表示では、まず `/api/v1/portfolio` だけ使えばよい」とあります。
`openapi.yaml` には載せていません。

## 起動の I/F — URL とクエリ 🟢

API の前に、**新 GUI がどう起動されるか**もサーバ側の文書で決まっています。

| URL | 役割 |
|---|---|
| `/external/` | 新 GUI 本体。別リポジトリのビルド成果物（またはモック）を置く |
| `/external-host` | 新 GUI を iframe で開くホスト画面。**クエリを引き継ぐ** |
| `/` | 既存のトップ画面（進捗会議マトリクス）。維持対象 |

### 起動クエリ（`UI-COMMON-10`）

| クエリ | 値 | 必須 | 画面側での扱い |
|---|---|:---:|---|
| `view` | `gantt` / `network` | 任意 | 初期表示タブ。省略時は `gantt` |
| `projectIds` | カンマ区切り | **実質必須** | 表示するプロジェクト。**そのまま `GET /portfolio` に渡す。** 省くと全件（47 案件）で重い |
| `teamId` | 文字列 | 任意 | 予約。現時点では使わない（将来の機能軸フィルタ用） |
| `asOf` | ISO 日時 | 任意 | 判定基準日。そのまま `GET /portfolio` に渡す |

例: `/external-host?view=network&projectIds=17,49`

> これにより、以前の「ファイルを開く画面」（`UI-OPEN-*`）は**不要になりました。**
> どのプロジェクトを見るかは、ホスト画面（既存のトップ画面）側で決まって渡されてきます。

## 各 API の説明

### `GET /health` — 疎通確認 🟢

```json
{ "status": "ok" }
```

起動時に最初に呼びます。失敗したときの見せ方は [`22-errors.md`](22-errors.md)。

---

### `GET /meta` — サーバ側の情報 🟢

```json
{
  "server": "bm3-xml-workbench",
  "version": "0.1.0",
  "capabilities": ["portfolio-mock-read", "bm3-xml-derived-json"],
  "writeEnabled": false
}
```

**`writeEnabled` がいちばん重要です。** サーバ側の文書にはこうあります。

> `writeEnabled=false` の間、フロント側は BM3 反映・BMD 生成・保存を実行可能にしないこと。

画面側は起動時にこれを読み、`false` なら保存ボタンを**「未実装（画面内ドラフト）」の表示**にします（`UI-DIFF-09`）。
編集そのものは今まで通りできます。変更は画面側にたまり、ブラウザを閉じると消えます。

`capabilities` の各名前の意味は未確認なので、画面側は名前で判定しません。`writeEnabled` だけを見ます。

---

### `GET /portfolio` — 複数プロジェクトの計画を読む 🟢

**新 GUI が使う主たる API です。** 起動クエリの `projectIds` と `asOf` をそのまま渡します。

```
GET /api/v1/portfolio?projectIds=17,49&asOf=2026-09-04
```

応答の形（各項目の意味は [`20-data-model.md`](20-data-model.md)）:

```json
{
  "planId": "bm3-portfolio",
  "revision": "bm3-2-...",
  "sourcePath": "C:\\...\\bm3-xml-workbench\\raw",
  "projects": [ { "id": "17", "name": "BEV step3 AMP", "color": "#4a7fd0" } ],
  "tasks":    [ { "id": "17:194", "name": "...", "kind": "task", "parentId": "17:158", "projectId": "17", "...": "..." } ],
  "deps":     [ { "from": "17:194", "to": "17:159" } ],
  "critical": [ "17:1", "17:158" ],
  "today":    "2026-09-04",
  "errors":   []
}
```

#### 画面側が守ること（サーバ側の文書「サーバ I/F に合わせる必要があるもの」より）

1. 起動時に `/api/v1/portfolio` を読む
2. `projectIds` クエリを保持して API へ渡す
3. `projects / tasks / deps / critical` の **ID を変更せず**内部状態へ入れる
   — `{ProjectId}:{TaskId}` は依存関係とクリティカルチェーンのキーでもある
4. `revision` を保持する（将来の保存 I/F で使う予定）
5. `writeEnabled=false` の間はサーバ側へ保存しない

#### 一部が読めなかったとき

XML の解析に失敗したプロジェクトがあっても **200 で返り、`errors[]` にその旨が入ります。**
そのプロジェクトのタスクは応答に含まれません。画面側は**必ず利用者に伝えます**（`UI-COMMON-11`）。
黙って一部だけ表示すると、「そのプロジェクトは作業が無い」と誤解されます。

#### 暫定値であることが明記されている項目

サーバ側の文書が「暫定」「推定」と書いている項目です。画面側はこれらを**判定に使いません**（表示のみ）。

| 項目 | 何が暫定か |
|---|---|
| `progress` | BM3 の正式な進捗率ではなく、期間と残日数からの派生値 |
| `kind` | BM3 の TaskType と期間ゼロから推定 |
| `priority` | クリティカルなら `高`、それ以外 `中` という表示用の値 |

### `PUT /plans/{planId}` — 保存 🔴 **未実装**

**サーバ側で未実装です。** 形はこちらの想定のまま残しています。

分かっていること:
- `revision` が応答に含まれる → 版の照合（`If-Match`）は**できる可能性が高い**（`Q-005`）
- `planId` は現時点で常に `bm3-portfolio`

分かっていないこと:
- 差分を送るのか、全文を送るのか（`Q-015`）
- サーバ側の文書に列挙された「未確定の操作」（タスク追加・BMD 生成・BM3 アプリでの保存支援・
  横断リンクの永続保存・割り込みタスク生成・タスク分割・循環承認）が、どの API に対応するのか

`409` を受け取ったときの復帰手順（[`../ui/13-diff.md`](../ui/13-diff.md) の `UI-DIFF-06`）は、
実装されたときのためにそのまま残しています。

---

### `POST /plans/{planId}/validate` — 検証 🔴 **未実装**

**サーバ側で未実装です**（`Q-014`）。画面側でできる検証（依存の循環）は画面側で行っています。

## 実物と突き合わせるときの手順

読み込み側は済みました。**次は書き込み側です。**

1. サーバ側が保存 I/F を実装したら、[`received/`](received/) に原文を置く
2. [`openapi.yaml`](openapi.yaml) の `write` タグの操作を実物に差し替える（正はこちら）
3. この章を直す
4. `writeEnabled` が `true` を返すようになったら、`UI-DIFF-09` の表示を外す
5. 確定度マーカーを 🔴 から 🟢 に上げ、[`../90-open-questions.md`](../90-open-questions.md) に結論を追記する<!--legend-->
