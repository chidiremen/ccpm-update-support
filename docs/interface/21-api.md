# API 仕様（解説版）

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。
> **機械可読な正は [`openapi.yaml`](openapi.yaml) です。**この章はその読み物版です。

## ⚠️ この章の全体が推測です

サーバ側の実物が未入手のため、**[画面仕様](../ui/10-screens.md)から必要な操作を逆算して**
仮に置いたものです。実物と照らして差し替えてください。

## この API はどこから来たか

**画面の操作から導いています。** 各 API には
「どの画面操作のために存在するか」を明記しました。

これにより、後で実物と突き合わせたとき:

- **想定と違った API** → どの画面が影響を受けるかが分かる
- **どの操作からも参照されない API** → 不要だと分かる
- **サーバ側にない API** → その画面操作をどう実現し直すかを考えられる

## 一覧

| メソッド | パス | 用途 | 由来する画面操作 | 確定度 |
|---|---|---|---|:---:|
| `GET` | `/health` | 疎通確認 | 起動時 | 🔴 `Q-002` |
| `GET` | `/meta` | サーバ側の版と対応機能 | 起動時 | 🔴 `Q-002` |
| `POST` | `/plans` | 計画ファイルを開く | `UI-OPEN-01` `UI-OPEN-02` | 🔴 `Q-004` |
| `GET` | `/plans/{planId}` | 現在の計画を取得 | `UI-GANTT-01` `UI-NET-01` `UI-DIFF-06` 複数プロジェクトの全操作 調整パネルの全操作 | 🔴 `Q-003` |
| `PUT` | `/plans/{planId}` | 計画を全文置換（保存） | `UI-DIFF-03` | 🔴 `Q-005` |
| `POST` | `/plans/{planId}/validate` | 検証（保存しない） | `UI-DIFF-02` | 🔴 `Q-014` |
| `POST` | `/plans/{planId}/save` | ファイルへ書き出し | `UI-DIFF-03` | 🔴 `Q-015` |
| `DELETE` | `/plans/{planId}` | 編集セッションを閉じる | 画面を閉じる | 🔴 `Q-004` |

すべて `http://127.0.0.1:{ポート}/api/v1` の下に置きます（→ `Q-002`）。

### 増えるかもしれない呼び出し（まだ書いていません）

**画面側の都合で必要になるかもしれないが、サーバ側に有るかどうかで形が決まる**ものです。
決め打ちで書くと外れたときに画面側まで巻き込むので、確認できるまで `openapi.yaml` には入れません。

| 用途 | 由来する画面操作 | 決め手 |
|---|---|---|
| 日程の再計算（保存せずに） | `UI-GANTT-11` `UI-CONNECT-*` `UI-ADJ-02` | `Q-026` |
| 調整メモを計画ファイルの外に残す | `UI-ADJ-05` | `Q-037` |
| 複数の計画ファイルを同時に開く | `UI-OPEN-01` `UI-GANTT-27` | `Q-035` |
| 項目カタログを受け取る | `UI-COMMON-06` | `Q-032` |

### なぜ `/api/v1` で括るのか

**画面を配信する経路と、API の経路を分けるため**です。

分けておけば、将来 AI から叩くようになったときも、
将来画面側とサーバ側を別々に動かすようになったときも、
**API 側は手を入れずに済みます。**

`v1` を付けているのは、後で互換性のない変更が必要になったとき、
古い画面を壊さずに `v2` を並行提供できるようにするためです。

## 各 API の説明

### `POST /plans` — 計画ファイルを開く

計画ファイルを読み込み、編集セッションを始めます。

**返ってくるもの**: `planId`（以降の操作で使う識別子）と
`revision`（版の印）と `xml`（計画の中身）。

> ⚠️ **`revision` は必ず保持してください。** 保存するときに必要です。
> これを捨ててしまうと、他人の変更を消す事故を防げなくなります。

#### 最優先の確認事項 (`Q-004`)

**ファイルの指定方法が未確定です。**

現在は「サーバ側から見えるファイルのパスを指定する」形で書いていますが、
**ブラウザは安全上の理由から、利用者が選んだファイルの絶対パスを
画面側に教えてくれません。**

つまり、パス指定にするなら次のどちらかが必要です:

1. 利用者にパスを**手で入力**してもらう
2. サーバ側が「開けるファイルの一覧」を返し、そこから**選ばせる**

あるいは、ファイルの中身を送る方式にすればこの問題は起きませんが、
その場合はサーバ側が「どこに書き戻すか」を知る手段が別途必要になります。

**この 1 点で画面の作りが変わるため、真っ先に確認してください。**

---

### `GET /plans/{planId}` — 現在の計画を取得

サーバ側が持っている最新の計画を返します。

**使う場面**:
- 画面を再読み込みしたとき
- **保存が衝突したあと、最新を取り直すとき**（`UI-DIFF-06`）

#### 複数プロジェクトの表示と調整パネルに、新しい API は要りません 🔴推測 (`Q-035`)

並べ方の切り替え（`UI-GANTT-27`）・担当の付け替え（`UI-GANTT-28`）・絞り込み（`UI-GANTT-29` `UI-COMMON-08`）・
ネットワーク図の枠と強調（`UI-NET-18` `UI-NET-19`）・調整パネル（`UI-ADJ-*`）は、
**ここで受け取ったデータを画面側で並べ替え・絞り込み・編集しているだけ**です。
サーバ側への呼び出しは増えません。

担当の付け替えや調整パネルでの日程の試行は、他のセル編集と同じく**画面側にたまり、
保存（`PUT`）でまとめて送られます**。調整パネルの「適用」は計画への反映であって保存ではありません
（[`23-sequences.md`](23-sequences.md) の流れ 5）。

ただし**調整メモ**（`UI-ADJ-05`）は計画ファイルの外に置くものです。
残す場所がサーバ側にあるなら呼び出しが 1 つ増えます（→ `Q-037`）。

⚠️ **ただし `Q-035` の答え次第で変わります。**

| プロジェクトの持ち方 | この API への影響 |
|---|---|
| 1 つの計画ファイルに複数のプロジェクト | **影響なし。** いまのままで足ります |
| プロジェクトごとに別ファイル | **複数の計画を同時に開く**必要がある。`POST /plans` とこの API の呼び方が変わります |

**どちらになるか分からないうちは、API を先に決めません。**
決め打ちで作ると、外れたときに画面側まで巻き込んで直すことになります。
画面仕様（[`../ui/15-multi-project.md`](../ui/15-multi-project.md)）は
**どちらでも変わらない**書き方にしてあります。

---

### `PUT /plans/{planId}` — 計画を置き換える（保存）

計画の XML を**全文置き換え**ます。部分更新はできません。

#### `If-Match` が保存事故を防ぐ仕組み

読み込んだときの `revision` を `If-Match` ヘッダーに入れて送ります。

```
（利用者 A が読み込む）      → revision "r7" を受け取る
（利用者 B が保存する）      → サーバ側は "r8" になる
（利用者 A が保存を試みる）  → If-Match: "r7" を送る
                            → サーバ側は "r8" なので食い違う
                            → 409 で拒否。B の変更は守られる
```

**この仕組みがないと、後から保存した人が前の人の変更を黙って消します。**
計画の全文を置き換える設計では、これは必ず起きます。

`409` を受け取ったときの復帰手順は
[`../ui/13-diff.md`](../ui/13-diff.md) の `UI-DIFF-06` を参照してください。
**利用者の変更を捨てさせないこと**が肝心です。

> ⚠️ サーバ側がこの仕組みに対応しているかは未確認です（→ `Q-005`）。
> 対応していない場合、この事故は防げません。
> その場合の落としどころも `Q-005` に書いてあります。

---

### `POST /plans/{planId}/validate` — 検証する

保存前に、計画として妥当かを確かめます。**ファイルは変更しません。**

#### 問題が見つかっても `200` を返します

これは意図的です。**「検証できたこと」自体は成功**だからです。

問題の有無は本文の `valid` で判断してください。
`400` や `422` を返すと、「検証の仕組みが壊れている」のか
「計画に問題がある」のかを画面側が区別できなくなります。

#### エラーと警告を分けます

- **エラー** — 保存できない。直すまで先へ進めない
- **警告** — 保存できる。利用者の判断に委ねる

> ⚠️ サーバ側に検証の仕組みがあるか、どこまで見るかは未確認です（→ `Q-014`）。
> なければ、画面側でできる範囲だけを確かめます。

---

### `POST /plans/{planId}/save` — ファイルへ書き出す

> ⚠️ **この API は不要かもしれません**（→ `Q-015`）。

`PUT /plans/{planId}` がその場でファイルに書き込むなら、この API は要りません。

分けるのは「サーバ側のメモリ上で編集し、明示的に書き出す」作りの場合です。
別名保存にも対応しやすくなります。

**サーバ側がどちらの作りかを確認し、不要なら削除してください。**

---

### `GET /meta` — サーバ側の情報

サーバ側の版と、**対応している機能の一覧**を返します。

#### `capabilities` があると確認事項が減ります

サーバ側が「版の照合に対応しているか」「検証できるか」
「クリティカルチェーンを計算できるか」を返してくれれば、
**画面側は実行時に判定して、使えない機能を隠せます。**

```json
{
  "serverVersion": "1.4.2",
  "capabilities": {
    "optimisticLock": true,
    "validation": true,
    "criticalChain": false,
    "saveAs": false
  }
}
```

これがあると、サーバ側の版が上がって機能が増えたときも、
**画面側を直さずに新機能が使えるようになります。**

> ⚠️ サーバ側がこれを返せるかは未確認です（→ `Q-002`）。
> 返せないなら、画面側に決め打ちで書くことになります。
> **返せるようにしてもらう価値は高い**ので、交渉する余地として覚えておいてください。

## 実物と突き合わせるときの手順

社内環境に戻ったら、次の順で進めてください。

1. **[`../90-open-questions.md`](../90-open-questions.md) を上から確認する**
   — `Q-001`（実ファイル）と `Q-004`（開き方）が最優先です
2. **[`openapi.yaml`](openapi.yaml) を実物に合わせて直す**（正はこちら）
3. **この章を直す**（読み物として辻褄を合わせる）
4. **[`20-data-model.md`](20-data-model.md) を実ファイルで差し替える**
5. **確定度マーカーを 🔴 から 🟢 に上げる**<!--legend-->
6. **[`../CHANGELOG.md`](../CHANGELOG.md) に記録する** — いつ・何を・なぜ
7. `bash scripts/check-spec.sh` を実行し、残りを確かめる

> **この 3 点セット（`openapi.yaml` / 解説 / CHANGELOG）は必ず一緒に直してください。**
> どれか 1 つだけ直すと、以降の読み手が「どれが正しいのか」を判断できなくなります。
