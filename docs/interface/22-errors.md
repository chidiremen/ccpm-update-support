# エラーの扱い

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。

## 基本方針

**すべてのエラーを同じ形で返します。**
画面側はこの形だけを扱えばよくなり、エラー処理が 1 か所にまとまります。

```json
{
  "code": "REVISION_CONFLICT",
  "message": "他の変更と重なっているため保存できませんでした",
  "details": {
    "currentRevision": "r9",
    "expectedRevision": "r7"
  }
}
```

| 項目 | 役割 |
|---|---|
| `code` | **画面側が分岐に使う。** 機械が判別するための不変の文字列 |
| `message` | 人が読む説明 |
| `details` | 種類ごとの追加情報 |

### `message` をそのまま表示してよいか 🔴推測 (`Q-024`)

⚠️ **サーバ側の `message` をそのまま利用者に見せるかは要検討です。**

サーバ側のメッセージが技術的すぎる場合（例:「XML パースエラー: 予期しないトークン」）、
利用者には意味が通じません。

**方針**: 画面側は `code` ごとに**自前の説明文**を持ちます。
`message` は補足として、詳細を開いたときに見せます。

これなら、サーバ側の文言が変わっても画面側の表示は安定します。

## エラーコードの一覧 🔴推測

⚠️ **すべて仮置きです。** サーバ側が実際に返すコードは未確認です（→ `Q-025`）。

| コード | HTTP | 起きる場面 | 利用者に見せる内容 | 復帰できるか |
|---|:---:|---|---|:---:|
| `PLAN_NOT_FOUND` | 404 | 指定した計画が存在しない | 「計画が見つかりません。開き直してください」 | 開き直す |
| `FILE_NOT_FOUND` | 404 | ファイルが指定の場所にない | 「ファイルが見つかりません」＋パスを表示 | パスを直す |
| `FILE_NOT_ACCESSIBLE` | 403 | 読み書きの権限がない | 「ファイルを開く権限がありません」 | 権限を直す |
| `INVALID_XML` | 422 | XML として壊れている | 壊れている行と列を示す | 直せば可 |
| `SCHEMA_MISMATCH` | 422 | 想定する形式に沿っていない | 「対応していない形式です」＋対応形式 | 不可 |
| `VALIDATION_FAILED` | 422 | 計画として矛盾がある | 問題箇所の一覧を表示 | 直せば可 |
| `REVISION_CONFLICT` | 409 | **他の変更と重なった** | 両方の変更を並べて選ばせる | **可（重要）** |
| `PRECONDITION_REQUIRED` | 412 | `If-Match` を送っていない | （画面側の不具合。利用者向けの文言は不要） | 画面側を直す |
| `INTERNAL_ERROR` | 500 | サーバ側の想定外の失敗 | 「問題が起きました」＋詳細を開ける | 再試行 |

---

## 特に重要なエラー

### `REVISION_CONFLICT` (409) — 保存の衝突

**これは失敗ではなく、事故を防いだ成功です。**

自分が読み込んだ後に、他の誰か（または自分の別ウィンドウ）が保存した、
ということを意味します。**保存は行われていません。**

> ⛔ **絶対にやってはいけないこと**
>
> - 利用者の変更を捨てる
> - 「保存に失敗しました」とだけ出して終わる
> - `If-Match` を外して強引に保存し直す（他人の変更を消すことになります）

**正しい対応**: 最新を取り直し、変更を突き合わせて、利用者に選ばせます。
手順は [`../ui/13-diff.md`](../ui/13-diff.md) の `UI-DIFF-06` にあります。

### `INVALID_XML` (422) — XML が壊れている

**どこが壊れているかを必ず示します。**
「XML が不正です」だけでは、利用者はどうしようもありません。

`details` に行番号と列番号が入る想定です（→ `Q-025`）。
XML を直接編集する手段があるなら、その位置へ飛ばします。

### `INTERNAL_ERROR` (500) — 想定外の失敗

利用者には短く伝え、**詳細を開けるようにします。**
社内で問い合わせるとき、詳細があると原因究明が早くなるためです。

**未保存の変更は保持したままにしてください。** 再試行で救えることが多いためです。

## 通信そのものが失敗した場合

サーバ側が応答しない場合（サーバ側が起動していない、落ちた）は、
HTTP のエラーではなく**通信の失敗**として画面側に届きます。

| 状況 | 利用者に見せる内容 |
|---|---|
| サーバ側に繋がらない | 「サーバ側が起動していない可能性があります」＋起動手順への案内 |
| 応答が返らない | 「応答がありません」＋再試行の手段 |

**このとき未保存の変更は絶対に捨てないでください。**
サーバ側が復帰すれば、そのまま保存できます。

⚠️ サーバ側の起動方法・確認方法が未確認です（→ `Q-002`）。
利用者に案内する文言は、それが分かってから確定します。

## エラー表示の設計指針

### 3 段階で使い分ける

| 段階 | 使う場面 | 例 |
|---|---|---|
| **画面内に表示** | その場で直せる。作業を止めない | 検証の警告、入力の誤り |
| **通知バー** | 知らせたいが作業は止めない | 保存できた、再接続した |
| **ダイアログ** | 判断を求める。作業を止める | 保存の衝突、未保存のまま閉じようとした |

**ダイアログは最小限にします。** 多用すると読まずに閉じられ、
本当に重要なときに効かなくなります。

### 次にすべきことを必ず書く

「エラーが発生しました」だけでは、利用者は動けません。
**何が起きたか**と**次に何をすればよいか**を必ずセットで示します。
