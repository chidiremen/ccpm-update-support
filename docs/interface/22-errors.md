# エラーの扱い

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。

## この章の現在の状態

**2026-09-04 にサーバ側の I/F 一覧を受領しました。** 分かったことは 2 つです。

1. **読み込み（`GET /portfolio`）は、一部が失敗しても 200 で返り、`errors[]` に理由が入る** 🟢
2. 保存・検証は未実装なので、それらのエラーの形は**依然として不明** 🔴

エラー応答の共通の形（`code` / `message` / `details`）は、サーバ側の文書に記述がありません。
以前のこちらの想定は、保存 I/F が実装されるときの叩き台として下に残しています。

---

## 1. 読み込みで一部が失敗したとき 🟢 — `UI-COMMON-11`

```json
{
  "planId": "bm3-portfolio",
  "projects": [ ... ],
  "tasks": [ ... ],
  "errors": [
    { "projectId": "99", "message": "No XML file found ..." }
  ]
}
```

**`errors[]` が空でなければ、そのプロジェクトのタスクは応答に含まれていません。**

画面側は**必ず利用者に伝えます。** 黙って残りだけ表示すると、
「プロジェクト 99 には作業が無い」と誤解されます。これはリソース調整の道具として致命的です。

| 見せ方 | 内容 |
|---|---|
| 画面上部に帯 | 「プロジェクト 99 が読み込めませんでした（表示されていません）」 |
| 帯を開くと | サーバ側の `message` をそのまま |
| 消せるか | 消せる。ただし凡例にはそのプロジェクトを**灰色**で残し、読めていないことが分かるようにする |

`message` は英語の技術的な文言（例: `No XML file found ...`）のようです。
そのまま見せるかは `Q-024` のまま。**まず「読めなかった」という事実**を日本語で出し、原文は補足にします。

---

## 2. 通信そのものが失敗したとき 🟢（起きることは確実。見せ方はこちらの方針）

`GET /health` や `GET /portfolio` が返ってこない、または 200 以外で返る場合です。

| 状況 | 起きること | 利用者に見せる内容 |
|---|---|---|
| サーバ側が起動していない | 接続できない | 「サーバ側に接続できません。起動しているか確認してください」 |
| `projectIds` が不正 | 200 以外、または `errors[]` | 「指定されたプロジェクトが読めません」＋ホスト画面へ戻る案内 |
| 応答が JSON として壊れている | 解釈できない | 「サーバ側の応答が読めません」＋詳細を開ける |

新 GUI はホスト画面（既存のトップ画面）から iframe で開かれるため、
**「ホスト画面に戻ってプロジェクトを選び直す」**が復帰の基本になります。

---

## 3. 保存・検証のエラー 🔴 未実装（こちらの想定）

サーバ側で保存 I/F が未実装のため、**現時点では起きません。**
`writeEnabled=false` の間、画面側はこれらの API を呼びません（`UI-DIFF-09`）。

実装されたときのために、以前の想定を残します。

### 共通の形（想定）

```json
{
  "code": "REVISION_CONFLICT",
  "message": "他の変更と重なっているため保存できませんでした",
  "details": { "currentRevision": "bm3-3-...", "expectedRevision": "bm3-2-..." }
}
```

| 項目 | 役割 |
|---|---|
| `code` | **画面側が分岐に使う。** 機械が判別するための不変の文字列 |
| `message` | 人が読む説明 |
| `details` | 種類ごとの追加情報 |

### コードの一覧（想定 → `Q-025`）

| コード | HTTP | 起きる場面 | 復帰できるか |
|---|:---:|---|:---:|
| `REVISION_CONFLICT` | 409 | **他の変更と重なった**。`revision` が応答にあるので、この照合は実現できる見込み (`Q-005`) | **可（重要）** |
| `VALIDATION_FAILED` | 422 | 計画として矛盾がある | 直せば可 |
| `PRECONDITION_REQUIRED` | 412 | `If-Match` を送っていない（画面側の不具合） | 画面側を直す |
| `INTERNAL_ERROR` | 500 | サーバ側の想定外の失敗 | 再試行 |

以前あった `PLAN_NOT_FOUND` `FILE_NOT_FOUND` `FILE_NOT_ACCESSIBLE` `INVALID_XML` `SCHEMA_MISMATCH` は、
**「ファイルを開く」操作が無くなった**ため消しました。読めない場合は上の 1. の形で来ます。

### `REVISION_CONFLICT` — 保存の衝突

**利用者の変更を捨てさせないこと**が肝心です。
復帰の手順は [`../ui/13-diff.md`](../ui/13-diff.md) の `UI-DIFF-06` にあります。

---

## `message` をそのまま表示してよいか 🔴推測 (`Q-024`)

受領した例（`No XML file found ...`）を見る限り、サーバ側の文言は英語の技術的なものです。

**方針**: 画面側は状況ごとに**自前の日本語の説明**を持ち、サーバ側の `message` は補足として詳細に出します。
これならサーバ側の文言が変わっても画面側の表示は安定します。

## エラー表示の設計指針

### 3 段階で使い分ける

| 段階 | 使う場面 | 例 |
|---|---|---|
| 帯（画面上部） | 作業を続けられるが知らせるべきこと | 一部のプロジェクトが読めなかった |
| ダイアログ | 作業を止めて判断してもらうこと | 保存の衝突（将来） |
| 画面全体 | 何もできないこと | サーバ側に接続できない |

### 次にすべきことを必ず書く

「エラーが発生しました」だけでは利用者は動けません。
**何が起きたか**と**次に何をすればよいか**を必ず組にします。
