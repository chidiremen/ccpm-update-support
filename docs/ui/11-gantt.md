# ガントチャート画面

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。
> 操作 ID の索引は [`10-screens.md`](10-screens.md) にあります。

## この画面の役割

**いつ、何をやるのか**を時間軸で見る画面。
計画の全体像をつかみ、日程の詰まり具合を確かめるために使います。

## 画面の構成

左に**タスクの一覧**、右に**時間軸の帯**を並べます。左右は縦スクロールが連動します。

```
┌─────────────────────────┬────────────────────────────────────────┐
│ タスク名        期間 担当 │  4月      5月      6月      7月          │
├─────────────────────────┼────────────────────────────────────────┤
│ ▼ 設計フェーズ    20d     │  ▭▭▭▭▭▭▭▭                              │
│   ├ 要件定義      8d  佐藤│  ▓▓▓▓                    ← クリティカル  │
│   └ 基本設計     12d  鈴木│      ▓▓▓▓▓▓                            │
│ ▼ 実装フェーズ    35d     │            ▭▭▭▭▭▭▭▭▭▭▭▭▭               │
│   ├ 画面側実装   20d  田中│            ▓▓▓▓▓▓▓▓▓▓                  │
│   └ サーバ側実装 15d  高橋│            ░░░░░░░                     │
│   試験           10d  佐藤│                        ▓▓▓▓▓           │
│   ▒ プロジェクトバッファ  │                             ▒▒▒▒▒▒      │
└─────────────────────────┴────────────────────────────────────────┘
   ▓ クリティカルチェーン   ░ 通常タスク   ▒ バッファ
```

## 操作の仕様

### `UI-GANTT-01` タスクを階層構造で一覧表示する 🔴推測 (`Q-008`)

タスクが親子関係を持つ（フェーズの下に個別タスクがぶら下がる）ことを想定しています。

- 親タスクは折りたたみ・展開ができる
- 親タスクの期間は、子タスクをすべて含む範囲として表示する
- 階層の深さに上限は設けない

⚠️ **そもそも計画ファイルに階層構造があるかが未確認です**（→ `Q-008`）。
階層がなく平坦な一覧であれば、折りたたみ機能は不要になります。

**表示する列**（🔴推測）: タスク名 / 期間 / 開始日 / 終了日 / 担当 / 進捗

⚠️ どの項目が実際に計画ファイルにあるかは未確認です（→ `Q-001`）。
進捗・実績の扱いがこのツールの対象かも未確認です（→ `Q-019`）。

### `UI-GANTT-02` 各タスクの期間を帯で表示する 🔴推測 (`Q-016`)

横軸の時間目盛りに合わせて、各タスクを帯で描きます。

**未確定の点** — 日付と期間の扱いは、計画ファイルの形式に完全に依存します:

- 日付の形式（`2026-04-01` 形式か、別の形か）
- 期間の単位（日か、時間か、人日か）
- **暦日と営業日のどちらで数えるか**（土日祝を飛ばすか）
- 稼働カレンダー（休業日）が計画ファイルに含まれるか

⚠️ 特に**営業日か暦日か**は、帯の長さが変わるため見た目に直結します（→ `Q-016`）。

### `UI-GANTT-03` クリティカルチェーンを強調表示する 🔴推測 (`Q-011`)

計画全体の長さを決めている一連のタスクを、他と区別できる色で示します。

**大きな未確定点**: クリティカルチェーンを**誰が計算するか**。

| 案 | 内容 | 影響 |
|---|---|---|
| **サーバ側が計算** | 計画ファイルに結果が入っている、または API が返す | 画面側は表示するだけ。楽 |
| **画面側が計算** | 画面側が依存関係をたどって求める | 画面側の実装量が増える。計算方法の取り決めが要る |

⚠️ CCPM のクリティカルチェーンは、**単なる最長経路ではなく資源の競合も考慮する**ため、
画面側で正しく計算するのは簡単ではありません。
**サーバ側が持っているのが望ましい**という立場で確認してください（→ `Q-011`）。

### `UI-GANTT-04` バッファを表示する 🔴推測 (`Q-010`)

バッファ（意図的に確保した余裕時間）を、通常のタスクと区別できる見た目で示します。

- **プロジェクトバッファ** — 計画全体の最後
- **合流バッファ** — 別の流れが合流する手前

バッファの**消費状況**（どれだけ使われたか）を見せられると、CCPM の運用上は有用です。
ただし実績データが計画ファイルにあるかは未確認です（→ `Q-019`）。

⚠️ そもそもバッファが計画ファイル上でどう表現されるか（専用の要素か、
特別な名前のタスクか、属性か）が未確認です（→ `Q-010`）。

### `UI-GANTT-05` タスクを選び、詳細を表示する 🔴推測

タスクをクリックすると、その全項目を右側または下部のパネルに表示します。

選択状態は**ネットワーク図と共有します**（`UI-COMMON-04`）。
ガントで選んだタスクは、ネットワーク図に切り替えても選択されたままです。

### `UI-GANTT-06` タスクの値を編集する 🔴推測 (`Q-006`)

⚠️ **この操作が API の形を最も大きく左右します。**

現在の想定では、やり取りするのは XML 文字列そのもので、部分更新はできません。
つまり **1 か所直すたびに全文を送り直す**ことになります。

これを踏まえた方針（初版）:

1. 編集は**画面側のメモリ上で行う**（サーバ側には送らない）
2. 変更はためておく
3. 「保存」を押したときに、**まとめて全文を送る**

この方式なら、部分更新の API がなくても成立します。
また、編集のたびに通信しないので動作も軽くなります。

**やってはいけないこと**: 1 項目編集するたびに全文を送信すること。
通信量が大きく、保存衝突も起きやすくなります。

⚠️ サーバ側にタスク単位の更新 API があるなら方針を変える余地があります（→ `Q-006`）。

### `UI-GANTT-07` 表示する期間の範囲を変える 🔴推測

日 / 週 / 月 の単位を切り替えて、拡大・縮小します。
計画全体が画面に収まる「全体表示」も用意します。

### `UI-GANTT-08` 依存関係を線で表示する 🔴推測 (`Q-009`)

タスク間の依存を、帯と帯をつなぐ線で示します。

依存関係には一般に 4 種類（前工程の終了後に開始、同時開始、同時終了、
前工程の開始後に終了）がありますが、**計画ファイルがどこまで表現できるかは未確認です**
（→ `Q-009`）。

線が多いと画面が見づらくなるため、初版は
**選択中のタスクに関わる依存だけを表示**します。全部表示に切り替える手段も用意します。

## この画面が必要とする API

| 操作 | 必要な API |
|---|---|
| 計画を表示する | `GET /api/v1/plans/{planId}` — XML を取得し、画面側で解釈する |
| 編集する | なし（画面側のメモリ上で完結） |
| 保存する | [`13-diff.md`](13-diff.md) を参照 |

⚠️ **クリティカルチェーンをサーバ側が計算する場合**、それを受け取る API が別途必要です。
`Q-011` の回答次第で、API を 1 つ追加することになります。
