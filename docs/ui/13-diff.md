# 変更内容の確認画面

> 用語は [`../00-glossary.md`](../00-glossary.md) で定義しています。
> 操作 ID の索引は [`10-screens.md`](10-screens.md) にあります。

## この画面の役割

**保存する前の関所**です。

計画ファイルは、壊すと影響が大きいものです。
「保存」を押した瞬間に書き込むのではなく、
**何がどう変わるのかを見せて、納得してから確定する**流れにします。

この画面は 3 つの役目を持ちます。

1. 変更点を見せる（`UI-DIFF-01`, `UI-DIFF-04`）
2. 保存できる状態か検証する（`UI-DIFF-02`）
3. 保存する。衝突したら復帰させる（`UI-DIFF-03`, `UI-DIFF-06`）

## 操作の仕様

### `UI-DIFF-01` 変更点を一覧で表示する 🔴推測 (`Q-013`)

**「XML の何行目が変わったか」ではなく、「計画として何が変わったか」を見せます。**

利用者が知りたいのは「`<duration>` タグが `12` から `15` になった」ではなく、
「基本設計の期間が 3 日延びた」だからです。

**変更の種類**:

| 種類 | 表示 |
|---|---|
| 追加 | 追加されたタスクと、その主要項目 |
| 削除 | 削除されたタスク名 |
| 変更 | 変わった項目のみ、変更前 → 変更後 |
| 依存の変更 | どのタスク間のつながりが増減したか |

**波及した影響も示します。** 期間を延ばした結果バッファが減る、
クリティカルチェーンが別の経路に移る、といった変化は、
利用者が直接操作していないため見落としやすいものです。

**差分を誰が計算するか**（🔴推測 `Q-013`）:

| 案 | 内容 |
|---|---|
| **画面側が計算**（初版） | 読み込んだ時点の状態を覚えておき、比較する。サーバ側の改修が不要 |
| サーバ側が計算 | 新旧の XML を送り、差分を返してもらう |

**初版は画面側で計算します。** 読み込み時点の状態を保持しておけば実現でき、
サーバ側に依存しないためです。

### `UI-DIFF-02` 保存前に計画を検証する 🔴推測 (`Q-014`)

保存する前に、計画として妥当かを確かめます。

**確かめたいこと**（🔴推測）:

- XML として壊れていないか
- 想定する形式に沿っているか
- 依存関係が循環していないか（A→B→C→A のような堂々巡り）
- 参照先のないタスクを指していないか
- 日付の前後関係が矛盾していないか

⚠️ **サーバ側に検証の仕組みがあるか、あるならどこまで見るかが未確認です**（→ `Q-014`）。

サーバ側が検証してくれるなら、`POST /api/v1/plans/{planId}/validate` を呼びます。
なければ、画面側でできる範囲（XML の妥当性、循環参照）だけを確かめます。

**検証結果は「エラー」と「警告」に分けます。**

- **エラー** — 保存できない。直すまで先へ進めない
- **警告** — 保存はできる。利用者の判断に委ねる

### `UI-DIFF-03` 計画ファイルに保存する 🔴推測 (`Q-015`)

保存の流れ:

1. 検証する（`UI-DIFF-02`）。エラーがあれば止める
2. 変更を反映した XML を組み立てる
3. `PUT /api/v1/plans/{planId}` に、`If-Match` で読み込み時の `revision` を添えて送る
4. 成功したら、新しい `revision` を受け取って保持する
5. 失敗が `409` なら `UI-DIFF-06` へ

⚠️ **上書き保存だけか、別名保存もできるかが未確認です**（→ `Q-015`）。
別名保存があるなら、保存先を指定する手段が要ります。

**保存前に元のファイルの控えを残すか**も検討事項です。
計画ファイルは重要なので、控えがあると安心ですが、
サーバ側の役目か画面側の役目かを決める必要があります（→ `Q-015`）。

### `UI-DIFF-04` XML の文字レベルの差分を見る 🔴推測

`UI-DIFF-01` の意味的な差分とは別に、**XML そのものの差分**も見られるようにします。

普段は折りたたんでおき、必要なときだけ開きます。
意味的な差分では表せない変化（属性の順序、空白、コメント）を確かめたいとき、
また画面側の不具合を疑うときに使います。

⚠️ **注意**: XML を読み込んで書き出すと、
利用者が変更していない箇所も見た目が変わることがあります
（属性の順序、改行、インデント、コメントの欠落）。

**これは大きな落とし穴です。** 1 か所だけ直したつもりが、
ファイル全体が書き換わったように見えると、利用者は不安になります。
また、そのファイルを別のツールで版管理している場合、差分が読めなくなります。

対策として、**元の書式をできるだけ保つ**方針を採ります。
実現できるかは XML の扱い方に依存するため、実装時に確かめます（→ `Q-023`）。

### `UI-DIFF-05` 個々の変更を取り消す 🔴推測

一覧の各項目から、その変更だけを取り消せるようにします。

「全部やり直し」しかないと、
1 つ間違えただけで作業をすべてやり直すことになるためです。

### `UI-DIFF-06` 保存が衝突したときに復帰する 🔴推測 (`Q-005`)

**自分が読み込んだ後に、誰か（または自分の別ウィンドウ）が保存していた場合**、
サーバ側は `409 Conflict` を返します。

このとき、**変更を捨てさせてはいけません。** 次の流れで復帰します。

```mermaid
sequenceDiagram
    participant U as 利用者
    participant F as 画面側
    participant S as サーバ側

    U->>F: 保存
    F->>S: PUT /plans/{id}  If-Match: "r1"
    S-->>F: 409 Conflict（現在は "r2"）
    F->>S: GET /plans/{id}
    S-->>F: 最新の XML と "r2"
    F->>F: 3 つを突き合わせる<br/>①読込時 ②自分の変更 ③最新
    F-->>U: 「他の変更と重なっています」<br/>両方の変更を並べて表示
    U->>F: どちらを採るか選ぶ
    F->>S: PUT /plans/{id}  If-Match: "r2"
    S-->>F: 200 OK（新しい版 "r3"）
```

**利用者に見せるもの**:

- 自分がした変更
- 自分が読み込んだ後に他で入った変更
- **両方が同じ箇所に触れているか**（重なっていなければ、そのまま両立できる）

⚠️ この機能はサーバ側が `revision` に対応していることが前提です（→ `Q-005`）。
対応していない場合、**後から保存した人が前の人の変更を消す**ことになります。
その場合は、少なくとも
「読み込んでから時間が経っています」という注意を出す程度の対処にとどまります。

## この画面が必要とする API

| 操作 | 必要な API |
|---|---|
| `UI-DIFF-02` 検証 | `POST /api/v1/plans/{planId}/validate` |
| `UI-DIFF-03` 保存 | `PUT /api/v1/plans/{planId}`（`If-Match` 付き） |
| `UI-DIFF-06` 復帰 | `GET /api/v1/plans/{planId}` |
| `UI-DIFF-01` 差分 | なし（画面側で計算） |
